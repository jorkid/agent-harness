# Agent Harness｜架构关键决策记录 V1.0

- 日期：2026-11-10
- 来源：窗口2架构设计讨论；上游 `docs/01-requirements.md` V1.0
- 标记说明：**批准**＝用户明确同意；**AI 补充并批准**＝AI 提出，用户明确接受；**建议待确认**＝不得当作最终决定。

| ID | 决策与理由 | 状态 | 起源/修改说明 |
|---|---|---|---|
| ADR-01 | 三层逻辑架构：请求入口 → Runtime → 基础能力层；基础能力层含 Model、Tool Manager、Session、Context，模块之间不直接调用，Runtime 统一协调。MVP 易于理解，减少模块相互耦合。 | 批准 | 用户首先提出模块及协调层；AI 指出依赖方向和“模型层”命名，用户明确批准修改。 |
| ADR-02 | 请求入口独立，接受用户 message 和 session_id；会话标识由系统管理，不由 LLM 生成或自由修改。 | 批准 | 用户提出独立入口及 session_id，AI 补充新建会话生成 UUID 的候选方式。 |
| ADR-03 | Runtime 输入 message + session_id，输出含 answer / session_id / status；内部维护 Messages、执行计数、模型响应、工具 Trace 与当前状态。 | AI 补充并批准 | 用户提出输入、仅回答文本输出和部分内部状态；AI 补充结构化状态与执行计数，用户在后续表示同意建议。 |
| ADR-04 | Tool Manager 负责注册工具（名称、描述、Schema、函数映射）、校验与执行；Runtime 注入可信 session_id；Todo 操作受 session_id 与 todo_id 双条件约束。 | 批准 | 用户提出注册表与函数映射，经过多轮讨论确认执行边界与隔离规则。 |
| ADR-05 | Session 持久化采用 JSON；每个 Session 保存 messages、todos、memory、summary。 | 批准 | 用户明确选择 JSON 和四项数据。每 Session 一个文件、原子写、顺序处理仍是工程建议，未独立批准。 |
| ADR-06 | Context 使用动态近期窗口：超过20条时以完整交互边界将旧消息 + 旧 Summary 滚动压缩，目标保留最近10条。 | 批准 | 用户原创动态窗口 10–20 方案；AI 补充完整工具消息边界和超长输入保护，用户明确接受。 |
| ADR-07 | 在压缩前从即将移出的历史提取重要 Memory；Memory 为简短但语义完整的信息，压缩与提取失败保留原历史；每次 LLM 请求注入本 Session 的有界 Memory。 | AI 补充并批准 | 用户提出提取再压缩及记忆召回；AI 补充表达规则、长度保护和失败保护，用户同意。 |
| ADR-08 | 每次用户请求最多 8 次 LLM 决策；Session 对话轮次不设固定上限，用 Context 控制。 | 批准 | 需求阶段曾未决，用户在架构阶段明确选择；8 不是工具调用次数。 |
| ADR-09 | 可恢复工具错误回传给 LLM 继续决策；Todo 写入不确定时先核查或停止，不盲目重试。 | 批准 | 用户明确选择。 |
| ADR-10 | Trace 记录模型提出的工具请求、实际执行、结果及异常；必要字段可追溯，不泄露密钥。 | 批准 | 用户明确选择。 |

## 尚未批准的设计或实现细节

- 具体模型供应商 / SDK / API、模型请求/响应适配代码。
- 请求入口采用 CLI 还是 FastAPI；创建/恢复 Session 的具体端点。
- JSON 每 Session 单文件路径、原子更新、并发限制与恢复实现。
- `messages` 长期完整档案与上下文裁剪后的表示方式。
- Memory 上限、冲突处理、摘要生成参数、Token 长度保护阈值。
- 工具参数 Schema、Todo 的 CRUD 数据格式、Trace 存储文件格式与状态枚举的最终取值。

## 变更管理

上述已批准的逻辑架构和策略不可由下游窗口擅自修改。后续编码和真实模型接口出现冲突时，记录问题、替代方案与影响，交由项目负责人决策。需求以 `docs/01-requirements.md` 为上游依据。
