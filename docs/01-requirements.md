# Agent Harness 笔试项目｜需求规格说明书

- 文档版本：V1.0（需求阶段整理稿）
- 日期：2026-11-09
- 阶段：窗口1｜需求分析
- 决策状态：依据用户已确认的需求清单整理；尚未澄清项单独标注，不将建议视为已批准架构
- 依据：用户提供的完整笔试要求、题目截图及本窗口讨论

## 1. 项目目标与范围

从零实现一个最小可用的对话 Agent：用户输入后，真实 LLM 能依据工具描述和参数 Schema，自主选择直接回复或调用工具；执行工具并读取结果后，可继续决策直至完成或达到适用的限制；支持同一用户的多个独立 Session、基本 Context 管理、异常处理和可核查的工具 Trace。

**MVP 边界：** 只实现题目要求的 Agent Runtime 及测试、文档交付；其他五个架构设计笔试模块不纳入此编码项目。核心 Loop 不使用 LangGraph、LangChain Agent、OpenHands、OpenClaw 等现成 Agent 框架；可使用常规 Python 库及真实 LLM API 的基础 SDK。

## 2. 优先级及术语

- **必须**：题目明确要求，或为满足明确要求而不可缺少的行为。
- **可选实现**：可以在满足必须要求的前提下自由选择的工具类型或增强功能。
- **执行轮次**：Agent 为处理一条用户输入而进行的 LLM 决策循环次数。
- **对话轮次**：同一 Session 内用户与 Agent 之间的连续交互轮数。
- **Session**：可恢复、拥有独立对话上下文及工具/待办数据的会话单位。
- **Trace**：可核查模型工具请求、工具实际执行与结果的日志/轨迹；不要求暴露模型隐藏的内部推理。

## 3. 功能需求及验收条件

### FR-01 Agent Loop 与真实模型决策｜必须

**描述：** 接收用户输入，将当前必要的上下文和工具能力提供给真实 LLM，由 LLM 选择直接回复或提出工具调用；系统执行工具并把可见结果反馈给 LLM，使其决定继续执行或输出最终答案。支持一条请求内连续调用多个工具。模型接口若提供可见的解释/推理字段，可按接口允许的方式解析；不得假定可读取隐藏推理。

- 成功案例：输入“计算 1+1，并把结果创建成待办”，工具执行轨迹表明完成计算和创建待办；对应 Session 中存在内容为“2”的待办，最终回复与实际状态一致。
- 失败案例：模型只回答“已经创建 2”，但没有执行 Todo 工具、列表中没有该条待办；或执行一次工具后没有根据结果继续完成必要步骤。
- 证据：真实 LLM 请求/响应的可观测字段、工具 Trace、待办最终状态。不得以模型自述替代执行证据。

### FR-02 工具注册和参数 Schema｜必须

**描述：** 系统具有工具注册机制，至少记录工具名称、描述、参数 Schema（类型、必填项及必要约束）和工具执行入口；LLM 获得与工具对应的可调用定义；系统能够解析 LLM 返回的工具名称与参数并调用正确工具，处理不合法或未注册的调用。

- 成功案例：注册的工具可被模型按其 Schema 选择并以有效参数调用，执行记录中能对应到正确工具及参数。
- 失败案例：模型返回不存在的工具名或缺少必填参数，系统仍执行了错误工具或直接崩溃；只有硬编码关键词匹配，没有实现题目所要求的注册能力。
- 证据：工具定义、实际模型工具调用响应、合法/非法参数测试记录。

### FR-03 至少三个工具（含 Todo）｜必须；具体选型可替换

**描述：** 至少提供三个可由模型调用的工具；Todo 为必须工具。当前拟选 **calculator、search（可 Mock）、todo**。其中 calculator/search 是当前 MVP 选择，并非题目指定必须选择的工具；若调整选型仍需满足“至少三个、Todo 必须存在”。

**FR-03a Calculator｜当前选型，非指定硬性工具**
- 成功案例：用户请求“用计算器计算 1+1”，模型调用 calculator 并返回 2，Trace 记录执行。
- 失败案例：结果虽为 2，但未发生实际 calculator 调用，却声称使用了计算器。

**FR-03b Search｜当前选型，允许 Mock**
- 成功案例：用户明确要求从外部搜索获取信息，Agent 调用 search；若使用 Mock，返回预设、可验证的结果并据此回答，Trace 可查。
- 失败案例：没有调用 search 却编造“搜索结果”，或者实际工具结果与回答不一致。
- 约束：Mock 结果须明确是模拟数据，不得伪装成实时外部搜索。

**FR-03c Todo｜必须**
- 成功案例：同一 Session 内创建“待办1”后能查询到；修改、删除操作能对指定待办产生正确状态变化，且有对应工具 Trace。
- 失败案例：Agent 声称创建/修改/删除成功，但实际状态未变化；操作错误对象或重复创建。
- 证据：增、删、改、查各至少一个成功测试及失败/不存在目标测试，核对工具状态。

### FR-04 Session 隔离与恢复｜必须

**描述：** 同一用户可打开至少两个相互独立的 Session；各自的对话历史、必要 Context、工具状态及 Todo 数据不串扰；恢复任一 Session 后可继续对话和操作原有状态。

- 成功案例：A 创建“写论文”，B 创建“买牛奶”；恢复 A 后仅查到“写论文”，B 仍仅查到“买牛奶”。
- 失败案例：A 读到/修改了 B 的待办；或关闭再恢复 A 后其对话和待办数据丢失。
- 证据：多 Session 交替操作、恢复前后查询结果与状态比对。

### FR-05 Context 管理：追问与状态延续｜必须

**描述：** 在同一 Session 中保留执行当前任务必要的用户输入、可见对话信息及相关工具结果，支持纯对话追问与需要再次调用工具的追问。不能将跨 Session 默认读取作为同一 Session 追问的验收标准。

- 成功案例（纯对话）：在同一 Session 先讨论作息，下一轮询问“刚才说的睡觉时间”，能结合该 Session 已保留信息回答。
- 成功案例（带工具）：同一 Session 创建“写论文”，下一轮说“把刚才那个改到明天”，Agent 确认正确目标并更新该待办。
- 失败案例：把“刚才那个”理解成另一 Session 的待办，或缺乏足够信息时擅自修改不确定的目标。
- 证据：连续对话用例、实际 Todo 状态以及 Trace。

### FR-06 Context 管理：基础压缩｜必须

**描述：** Context 超过设定长度/预算时，对不重要的较早对话进行基础压缩或取舍，保留近期相关消息和影响后续任务的关键事实；长期对话仍能延续必要状态。**不要求完整的用户画像、复杂记忆检索或专用向量数据库。**

- 成功案例：首轮约定“计算结果保留两位小数”；经多轮对话并触发压缩后，第 100 轮的计算回答仍遵守该约定；能够检查到该关键约定在可用于当前推理的信息中被保留或召回。
- 失败案例：压缩后丢失仍有效的关键约定，导致第 100 轮回答不遵守要求；或无论历史多长都无限追加 Context 而不做任何控制。
- 证据：压缩前后可检查的 Context/摘要或相关记录，以及实际后续对话行为。
- 注：n/m 轮、摘要方式、Memory 存储和召回策略在架构阶段决定，不预先规定。

### FR-07 最大轮次限制｜必须，**口径待澄清**

**描述：** 题目原文在 Context 管理下要求“最大轮次限制”，但未明确是“单次请求的 Agent 执行轮次”还是“Session 对话轮次”。用户目前倾向将其理解为**对话轮次限制**；同时接受额外设置 Agent 执行轮次上限的可能性。**现阶段两者均不写成已定实现方案**，架构阶段须确认具体限制对象及触顶行为，并至少确保 Agent 不会无限执行。

- 验收候选 A（若定义为对话轮次）：累计达到配置的 Session 对话轮次上限时，系统按预先说明的规则处理下一轮输入，不发生无界增长或异常崩溃。
- 验收候选 B（若定义为 Agent 执行轮次）：模型重复请求工具、始终不结束时，达到配置的单请求上限后安全终止并如实报告未完成。
- 失败案例：实际选定的限制不起作用，造成无限循环、无界增长，或触顶后错误地声称已完成任务。
- **未决：** 最终选择 A、B 或两者，以及触顶后的继续会话行为；不得在未决前据此设置精确测试预期。

### FR-08 基本异常处理｜必须

**描述：** 处理 LLM 请求异常、工具不存在/参数错误、工具执行失败或超时等基础异常；失败时系统给出明确且真实的状态，不以虚构默认结果冒充成功。可恢复错误可采用有界恢复策略，但不要求复杂的模型切换/降级系统。

- 成功案例：天气/搜索工具超时，Agent 或系统最终明确告知查询未成功，主流程不会因未捕获异常直接崩溃；对 Todo 创建结果不确定的超时，不能盲目重复执行造成重复待办。
- 失败案例：Todo 创建失败却回答“已创建”，或者响应超时后无条件再次创建，产生重复记录。
- 证据：可控故障注入、用户可见结果、异常 Trace 和最终状态检查。

### FR-09 工具 Trace / 日志｜必须

**描述：** 提供可核查的工具执行记录，能区分 LLM 提出调用、工具实际执行和执行结果/异常；足以支持定位调用顺序与任务是否真实完成，避免记录或泄露 API Key 等秘密。

- 成功案例：对“计算 1+1 并创建待办”，可查看相应工具调用顺序、工具名称、必要参数与结果/状态，并与最终待办状态一致。
- 失败案例：只记录模型最终答复“执行成功”，无法判断工具是否真的调用；或日志含明文密钥。
- 证据：真实执行产出的 Trace / 日志样本。

| NFR-02 | 使用真实 LLM API 进行运行和验证 | 必须 | 能展示真实模型驱动的一条成功调用链；Mock Search 不等于 Mock LLM |

## 6. 暂不实现 / 非强制增强

- 其他五个架构设计笔试模块。
- 复杂用户画像、语义检索、向量数据库或完整长期记忆平台。
- 模型故障后跨模型自动切换、复杂熔断与分布式容错。
- 真实联网搜索（当前选择 Mock Search 满足题目允许条件）。
- 多用户权限系统、复杂前端界面与企业级部署（题目未明确要求）。
- 主动访问其他 Session 的历史和待办（不属于本次“独立 Session”要求）。

以上只划定非强制范围，不禁止在完成 MVP 且经用户批准后增强。

## 7. 假设、约束与待澄清问题

1. **轮次限制的口径**：题目“最大轮次”含义未明确；用户偏向会话轮次，但 Agent 执行上限也有价值。进入架构阶段前明确 A/B/两者与触顶行为。
2. **Session 恢复的持久性边界**：必须可恢复；是否要求跨进程重启/跨设备恢复，题目未写清，先不扩大范围。
3. **Memory 的具体保存、压缩、召回方式**：题目要求说明与基础有效性，未指定具体算法、存储技术或固定 n/m。
4. **工具的实际集合**：当前选 calculator、search（Mock）、todo；如替换工具仍须保持至少三个和 Todo 必须存在。
5. **模型可见推理**：仅处理 API 实际提供的可见信息，不要求获取隐藏推理链。

## 9. 向架构设计窗口交接摘要

- **已确定需求**：自主实现 Agent Loop、真实 LLM、至少三个工具（Todo 必须）、注册+Schema、Session 隔离与恢复、Context 追问与基础压缩、异常、Trace、README/Prompt/测试交付。
- **尚未决定的实现问题**：具体目录/类/模块/数据库、Context 预算与压缩方式、Memory 保存与召回机制、超时策略、Session 持久化边界。
- **特别需要澄清**：最大轮次限制究竟是对话轮次、Agent 单请求执行轮次或两者，及上限处理方式。
- **不得擅自变更**：不使用现成 Agent 框架承载核心 Loop；Session 间待办相互独立；不伪造工具执行或测试结果；不泄露秘密；不将另外五个模块纳入编码范围。
